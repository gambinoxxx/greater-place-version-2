## Architecture Decisions

- Stack is Next.js 16.3.3 / React 19.2.0 / MUI 9.4.0 (not the original Next 13 / React 18 / MUI v5). Follows `architecture.md` "Version modernization decision"; nothing was upgraded in Phase 1 or 2.
- Root `app/` directory, no `src/` — the scaffold had `src/app`, so it was moved to match the documented architecture.
- Global theme is dark-only; no `colorSchemes`, no `next-themes` wiring, no OS light fallback. `CssBaseline enableColorScheme` declares `color-scheme: dark` so browser force-dark cannot invert light sections. The homepage dark → light → dark change is a scroll-driven atmosphere (see below), not a theme mode.
- `lib/theme.js` is a client module (`'use client'`) because the theme object contains functions and cannot be passed from a Server Component to `ThemeProvider` otherwise. `app/layout.js` stays a Server Component. Documented in `code-standards.md`.
- Fonts are referenced in the MUI theme and Tailwind through the `--font-fraunces` / `--font-manrope` CSS variables set in `app/layout.js`, so there is a single font registration point.
- `npm run build` is `prisma generate && next build` so the client is always generated before the build.
- Prisma schema uses `cuid()` ids, `createdAt` / `updatedAt` timestamps, no relations, and optional ImageKit ID/URL string fields for images. The datasource reads `DATABASE_URL` only; `directUrl` and any driver adapter are intentionally absent until decided.
- `.env` is gitignored; `.env.example` documents variable names only.
- Buttons are MUI theme variants (`solidRed`, `outline`, `solidWhite`), not a hand-rolled wrapper. Link buttons take a plain `href`; the theme sets `LinkComponent` to `next/link`. `component={Link}` cannot be passed from a Server Component (functions cannot cross the Server→Client boundary) — this failed a build during Phase 2.
- The category → accent-color mapping lives only in `components/CategoryTag.jsx`; the accent → Tailwind-class map lives in `lib/accents.js` (shared with `SectionHeader`). Tailwind therefore scans `lib/` as well as `app/` and `components/`.
- Accent colors are fills and rules, never body-text color on ivory (green, gold, teal fail contrast there); dark text on accent fills passes for all six.
- Tailwind v3 opacity modifiers must be on the default scale (5, 10, 20, 25, 30, 40, 50, 60, 70, 75, 80, 90, 95). Off-scale values such as `/15` and `/85` silently generate no CSS; this caused two bugs in Phase 2.
- `SiteHeader` watches a 1px band at the header's vertical midline (rebuilt on resize and route change) so exactly one `[data-theme]` section is "under" the header. Sections declare `data-theme="dark"` or `data-theme="light"`; `SiteFooter` is `dark`.
- Shared components take data as props only: no Prisma, Firebase, ImageKit, or `fetch` inside `components/`.
- The homepage route file is `app/page.js`; shared components are `.jsx`. The split is intentional. The roadmap previously said `app/page.jsx` and was corrected.
- Homepage data flow: Server Component queries Prisma via `lib/prisma.js` in one `Promise.all` and passes rows as props; `dynamic = 'force-dynamic'`; empty tables render explicit empty states; no seeded or invented rows. `createdAt` ordering is used where no display-order field exists. Documented in `architecture.md`.
- Events carousel is a native scroll-snap client component fed server-rendered cards as children, not `react-multi-carousel`.
- WhatsApp links come only from the server-side `WHATSAPP_NUMBER` env var via `lib/whatsapp.js`; the number is never hardcoded.
- Homepage backgrounds are a single scroll-driven page atmosphere (dark → light → dark) rather than per-section backgrounds: sections only declare `data-theme`, and text, border, and tint colors follow `--atmos-*` variables so content always contrasts with the current background. Do not add `transition` classes on wrappers around content (the text color flips at t = 0.5). Documented in `tailwind-conversion-notes.md` §13.
- Testing pattern for Prisma-backed pages: use a temporary schema in the same Neon database (append `schema=<name>` to the connection string, run `prisma migrate deploy`, seed clearly fake rows, then `DROP SCHEMA ... CASCADE`). Never write test rows into the `public` tables.
- Blog teasers use the existing `Post` model, not a new `Blog` model (owner-approved 2026-09-20): one content table for teasers and the future `/blog`. No schema change in Phase 4.
- Inner routes (`/programs`, `/classes`, `/training`) are plain dark pages: `data-theme="dark"` sections, no `PageAtmosphere`. The mockups are fully dark.
- Culture is a teaser over `Class` rows (`take: 4`) linking to `/classes`; no `Culture` model. FAQ copy is static (no model). The Pathway is the local constant `lib/pathway.js`.
- Accent colors on inner routes: gold for Pathway / Training, purple for Culture and Classes, none for Programs, the blog teaser, and the FAQ (no documented mapping). Per-stage colors from the mockups are not used. Documented in `ui-context.md`.
- Classes, Training, and Blog are intentionally not in the header nav (owner decision). Enrollment WhatsApp links come only from `buildEnrollHref()` / `WHATSAPP_NUMBER`.
- Seeding is done with the idempotent `prisma/seed.js` (create-if-missing by slug, never overwrite), not one-off commands, so it can be re-run safely.
- Events policy (from the mockup): upcoming events are listed soonest-first as rows; past events appear separately as "Past Highlights" rows (`Title — Year`). Both come from one query (`lib/events.js`); the homepage reuses it. Past rows carry `id=<slug>` so links to past events resolve. Documented in `architecture.md`.
- WhatsApp stays server-side only (`WHATSAPP_NUMBER`), not `NEXT_PUBLIC_`; there is exactly one source of the number.
- Anchor targets that sit inside `RevealOnScroll` use `scroll-mt-32` (not 24), because the 24px reveal offset settles after the browser scrolls and would otherwise leave them flush against the header.
- Connection pooler gotcha: `DATABASE_URL` is Neon's pooler, so temp-schema sessions leave `search_path=<temp schema>` on shared backends. After dropping a temp schema, run `RESET search_path` across a batch of fresh connections until all report `"$user", public`. Prisma's own queries are unaffected (schema-qualified); unqualified raw SQL is.
- `Post.body` is Markdown (owner-confirmed) and is rendered only by `components/MarkdownBody.jsx` via `react-markdown` with `skipHtml` and the library's `defaultUrlTransform`. Never use `dangerouslySetInnerHTML` for post content; never add `rehype-raw`. Documented in `code-standards.md` and `architecture.md`.
- Blog URL contract: `/blog?category=<Name>&q=<text>`; `category` is validated against `CATEGORY_NAMES`, `q` is trimmed to 100 characters, and LIKE wildcards in `q` are escaped (Prisma's `contains` does not escape them).
- The blog's client surface is exactly one component, `ShareRail` (props `path`, `title`); everything else on `/blog` and `/blog/[slug]` is a Server Component.
- Bad slugs: a NUL byte in a slug would make Postgres throw (HTTP 500), so `getPostBySlug` returns null for such (and over-200-character) slugs and the page 404s.
- API convention (documented in `code-standards.md`): validate on the server before any DB call with rules in a pure shared module; `{ data, error }` with `error: { message, fields? }`; correct 400/413/415/500 codes; never return raw DB errors; JSON endpoints require `application/json` and cap body size.
- Contact channels are env-only and hidden when unset or malformed (`WHATSAPP_NUMBER`, `CONTACT_EMAIL`), never hardcoded; `/contact` is `force-dynamic` so a changed variable needs no rebuild.
- A honeypot returns the normal success response and stores nothing, so bots get no signal.
- Better temp-schema testing: use Neon's direct (non-pooler) endpoint plus `?schema=<temp>`; it left no `search_path` residue on the pooler in Phase 7 (the Phase 5 leak came from pooled sessions).

- `/our-story` splits content by shape: fixed prose is hardcoded JSX; only the team is database-backed (one `TeamMember` query feeding the founder strip and the leadership list). No value or history content was turned into a model.
- Mockup colour on the four focus-area tiles was dropped: it would assign accent colours to programme names, which `ui-context.md` §4 forbids. Tiles are neutral (`bg-atmos-tint`, `border-atmos-line`).
- Person text (names, roles) uses `overflow-wrap: anywhere`, not `break-words`: `break-words` does not reduce min-content width, so it does not stop a flex row or grid track from widening the page.
- Model queries are schema-qualified but raw `current_schema()` reports `public` even with `?schema=` set, so a seed guard must check the URL's `schema` parameter (not `current_schema()`), and cleanup verification should count `public."TeamMember"` explicitly.

- Rendering approach: an `<img srcset>` built by `@imagekit/javascript` (`getResponsiveImageAttributes`), not `next/image` with a loader and not the extra `@imagekit/next` package. It avoids a second optimisation hop, needs no `next.config.js` `remotePatterns`, and adds no dependency.
- The URL endpoint gate lives in `isImageKitUrl`: the SDK's `buildSrc` appends `?tr=` to any absolute URL (including foreign hosts) and would double-apply an existing `tr`, so only URLs under our endpoint (compared as origin plus path prefix through `URL`) with no transformation get transformed. Everything else is left exactly as stored.
- The auth route returns the public key in its response instead of exposing a `NEXT_PUBLIC_` variable, so all three ImageKit variables stay server-side and changing them needs no rebuild.
- `expire` for an upload signature is an absolute Unix time (ten minutes ahead), not "seconds from now" as the SDK JSDoc claims; passing a relative value silently produces an already-expired signature.
- Do not rely on `error.constructor.name` for SDK errors: the production build minifies class names. Use `instanceof` with the classes the SDK exports.
- Test technique: to test browser uploads without an account, map `upload.imagekit.io` to a local HTTPS server with Chrome flags (`--host-resolver-rules=MAP upload.imagekit.io 127.0.0.1:8443 --ignore-certificate-errors`) and have that server verify the HMAC signature, expiry, and token reuse. Remember that the CDP `Runtime.evaluate` helper awaits promises (`awaitPromise`), so a test that must act mid-upload has to fire the upload without returning its promise.

- Authentication is Clerk and authorization is an email allowlist (`ADMIN_ALLOWED_EMAILS`); being signed in to Clerk never admits anyone (Clerk sign-up is open by default). Firebase is not used and was removed.
- Next 16: the gate is `proxy.js` (`middleware.js` is deprecated and renamed). `clerkMiddleware()` throws on every request when its keys are missing, so `proxy.js` (a) only matches protected paths and (b) returns 503 itself when Clerk is unconfigured instead of calling Clerk. Public routes, `/sign-in`, and `/not-authorized` never run it.
- `<ClerkProvider>` is rendered only when both keys exist: unconditionally it would throw during the production build and start Clerk's keyless mode (an external provisioning call) in `next dev`.
- The allowlist decision is a pure function (`lib/admin-access.js`) shared by the proxy and `getAdminSession()`, and is tested without Clerk. It fails closed at every step (unconfigured, empty list, unknown email, failed lookup).
- Clerk's `auth()` throws on routes the proxy does not cover, so `getAdminSession()` can never silently admit a request on an uncovered route.
- `/not-authorized` is outside `/admin` on purpose (a page under `/admin` would redirect to itself), and it shows no allowlist details.
- Testing technique without a Clerk account: well-formed but nonexistent-instance keys (`pk_test_` plus the base64 of `<host>$`) let the whole configured code path (build, static prerender, handshake redirects, 401s, forged-token rejection) be exercised; real sign-in still needs a real dev instance. Beware `echo "====..."` in zsh (it is treated as a command).
- `npm update` follows caret ranges across minors (`^19.2.0` allowed React 19.3.0): pin exact versions when a specific patch is intended.

- Admin CMS pattern: every admin page starts with `requireAdminPage()`, every write handler is an `adminRoute()` (often via `crudRoutes()`), and validation is one pure module shared by browser and server. New admin routes under `/admin` or `/api/admin` need no proxy change (wildcard matcher), which Unit 10 confirmed.
- Drafts are a column (`Post.isPublished`), not a separate table, and public queries filter on it in one place per query. A future public Post query that forgets the filter would expose drafts: grep for `prisma.post` when adding one.
- Programs and Classes stay two models behind one admin section, distinguished by `?type=` / `?tab=`; the API is one endpoint set per model so a Program id can never be edited as a Class.
- Admin uploads use the same signed flow as Phase 9; the folders are `/posts`, `/events`, `/programs`, `/classes`, `/library`. Tests rewrote the folder to `/phase11-test/...` in the browser (an XHR `send` hook) to stay inside the approved test area.
- Layout lesson: `sr-only` inside an `overflow-x-auto` table needs a positioned (`relative`) wrapper; grids need `grid-cols-1` as the base column template.
